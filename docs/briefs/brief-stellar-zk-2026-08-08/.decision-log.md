## 2026-08-08 (Discovery continued — critical verified finding)

User's dump for this session: pivot direction toward "privacy service provider, ZK-focused, Stellar-only"; question whether the project becomes moot once Stellar ships native privacy; deep research on latest Stellar protocol articles requested; Proof of Reserve analysis requested; 5 Starknet privacy apps supplied for feature-porting analysis (PokerStarks, StarkVote, semaphore-cairo, kiroshi, Mental Poker SDK).

Before continuing that strategic work, loaded `zk-proofs` skill for CAP-0074/0075 grounding, which flagged a version/API discrepancy against the README's "Protocol 25 shipped native BN254" claim. Verified directly against source, not the skill's static cache:

- **VERIFIED BUG (reproduced via actual `cargo build`, not inferred):** all three generated verifier contract templates (`groth16_verifier`, `ultrahonk_verifier`, `risc0_verifier`) call a `Bn254` API shape (`env.crypto().bn254().g1_from_bytes(...)`, `.g2_from_bytes(...)`, `.fr_from_bytes(...)`, `.g1_neg(...)`) that has **never existed** in any real `soroban-sdk` release.
- `soroban-sdk = "23.4"` (the pinned constraint in all three `Cargo.toml.tmpl`) resolves to 23.5.3 today, which has no `bn254` module at all (only `bls12_381`) — confirmed via `docs.rs` and the `rs-soroban-sdk` source at that tag, then reproduced as `error[E0599]: no method named 'bn254' found` via a real `stellar-zk init` + `cargo build` in a scratch dir.
- The `bn254` module was introduced at `soroban-sdk` **25.0.0** (aligns with the README's "Protocol 25" claim), but its real API is shaped differently: `from_bytes`/`to_bytes` are associated functions on the point/scalar types (`Bn254G1Affine::from_bytes(BytesN<64>)`, `Bn254G2Affine::from_bytes(BytesN<128>)`, `Bn254Fr::from_bytes(BytesN<32>)`), not methods on `Bn254` itself; negation is the `Neg` operator (`-point`), not a `g1_neg()` method. Confirmed by bumping the pin to `"25"` and getting a *different* set of `E0599` errors, then reading the real `crypto/bn254.rs` source at `v27.0.5`.
- Byte sizes are unaffected: G1=64B, G2=128B, Fr=32B, big-endian, Ethereum-compatible — matches what `CLAUDE.md` and the Rust `serializer.rs` crates already assume. This is a **contract-template glue-code bug**, not a cryptographic design bug — the fix is scoped to the three `.tmpl` files' Rust code + the `soroban-sdk` version pin, not the serializers.
- Root cause of why CI never caught it: `.github/workflows/ci.yml` only runs `cargo build --workspace` / `cargo test --workspace` against the 5-crate workspace. The contract templates are `include_str!`-embedded and only materialize into a real, independently-compiled crate when a user runs `stellar-zk init` — there is no CI step that scaffolds a project and builds it end-to-end.
- Reproduced identically for all three backends (groth16, ultrahonk, risc0) — same pin, same call pattern.

This finding was surfaced to the user directly, before continuing the strategic/privacy-roadmap discovery, since it affects the product's core working claim regardless of positioning.
